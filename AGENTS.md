## Deploying kiro-remote: the pipeline, deployment tasks and `needs-niko`

Every merge to `main` deploys `KiroRemoteDnsStack` and `KiroRemoteStack` through the deploy pipeline ([runbook](docs/pipeline.md)), built on [`@nikovirtala/deployment`](https://github.com/nikovirtala/ark/tree/main/packages/deployment): it runs `pnpm check`, deploys, runs the smoke checks and the pending deployment tasks, and on a failure rolls back and freezes itself. `deploy.toml` names everything the run uses. The pipeline itself (`KiroRemotePipelineStack`, `packages/pipeline`) is its own CDK app, deployed by hand once.

**You never deploy.** Your AWS access is read-only, and `scripts/deploy.sh` is Niko's break-glass path. You do not run `./scripts/pipeline.sh bootstrap`, `settings`, `unfreeze`, `run` or `forget` either: `deploy` refuses `run`, `unfreeze`, `forget` and `settings` when `ARK_AGENT` is set. You may read: `./scripts/pipeline.sh status`, `tasks` and `dry-run`, and `node packages/pipeline/scripts/smoke.ts --dry-run`.

**A pull request ends with smoke checks and deployment tasks, not a runbook of commands to run by hand,** wherever the step can be automated:

- **What every deploy should show is a check** in `packages/pipeline/src/smoke/checks.ts` (PASS, FAIL, INFO or SKIP). A check for a new task reports `SKIP` only when the task's output is missing from the stack, and the task's marker output goes in `[smoke] markers` in `deploy.toml`: a SKIP for a task that is in the deployed commit fails the run. A scheduled job that has not run yet on its first deploy is INFO, never FAIL (`changedWithin` from the package). A new AWS call in a check needs its action in the smoke role (`smokeStatements` in `packages/pipeline/src/pipeline-stack.ts`); `checks.test.ts` fails until it is there. Smoke runs as a read-only role that cannot read session data (no table item, no object, no log line, no secret value, no user): do not give it a way to.
- **A one-off step is a deployment task**, a file in `tasks/` ([the protocol](tasks/README.md)). It runs once, after the smoke checks pass, as a role it declares, defined in `packages/pipeline/src/task-roles.ts` with its cases (a refusal beside every grant) in `packages/pipeline/scripts/simulate-pipeline-policy.ts`. A failed task freezes the pipeline and is not rolled back. Its summary holds counts and names, never data.
- **A step only a person can do stays a step** (the CodeConnections handshake, a secret whose value only Niko has, the GitHub App's settings, the Kiro API key, connecting an MCP client, clearing the freeze flag). The pull request gets the label `needs-niko` and lists the step under "After deploy". Nothing else goes there.
- **A new deploy setting** goes in `deploy.env.example`, `scripts/deploy.sh` (an `add_opt` line) and `[[settings.keys]]` in `deploy.toml`, and the pull request says Niko must run `./scripts/pipeline.sh settings` (`needs-niko`). A setting whose absence would delete something on deploy is REQUIRED in `deploy.toml`, with that effect; `packages/pipeline/src/config.test.ts` checks that `deploy.sh` and the schema name the same keys.
- **A change to the pipeline's roles** runs `./scripts/pipeline.sh simulate` (IAM's policy simulator, read-only) and puts its last line in the pull request.

What checks and tasks print stays in the build's CloudWatch log group (`/aws/codebuild/kiro-remote-deploy-run`). The ledger, the freeze flag, the notifications and the GitHub deployment descriptions hold ids, counts and names only.
